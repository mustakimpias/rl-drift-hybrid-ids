# Adaptive Machine Learning for Intrusion Detection: Overcoming the Limitations of Rule-Based Systems

**Framework:** Cost-Sensitive RL-Guided Drift-Triggered Active Learning Hybrid IDS

This repository contains code, configuration files, scripts, and thesis-ready
artifacts for an MSc thesis on label-efficient adaptive intrusion detection
using drift-triggered active learning and a lightweight RL controller.

The pipeline combines:

1. A **simulated rule-based layer** (a confidence-thresholded shallow decision
   tree standing in for a signature engine like Snort/Suricata; category-aware
   when the dataset carries a multiclass attack-category column).
2. An **ML layer** (batch baselines + River online models) that handles
   traffic the rule layer doesn't confidently match.
3. A **drift detector** (ADWIN and/or PageHinkley, config-selectable) monitoring
   the ML layer's prediction-error stream, shared between the standalone
   stream experiment and every hybrid arm.
4. **Active learning** strategies (random / uncertainty / drift-triggered
   uncertainty) that spend a limited label budget selectively, via a
   warm-up + batch-wise top-k query engine shared with the hybrid arms.
5. A **lightweight RL-lite controller** — tabular Q-learning over a small
   discretized state space (uncertainty, drift status, recent F1, recent
   FPR, remaining label budget) — that decides, per sample: query a label
   and update the model, update only if drift was detected, adjust the
   decision threshold conservatively, or do nothing. This is a decision
   policy, **not** the IDS classifier, and it never sees a sample's true
   label before choosing an action — only afterward, for reward bookkeeping.

No deep RL / DQN is used anywhere in this project, by design.

## Setup

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt
```

`xgboost` and `lightgbm` are optional — the pipeline detects their absence
and skips those baselines with a warning rather than failing.

## ⚠️ Synthetic data is for code testing only

By default (`allow_synthetic_fallback: false` in `configs/default.yaml`),
the pipeline **refuses to run** and exits with a clear error if `raw_dir`
has no usable dataset CSVs. This is intentional: there is no valid thesis
result without real data.

If you want to exercise the code without real data (e.g. to verify a change
didn't break anything), set `allow_synthetic_fallback: true` in your config
or pass a config that does — but every table this produces gets a
`synthetic_data=true` column, and the report prints a large warning banner.
**These numbers must never be cited as thesis results.**

## ⚠️ Do not hand-edit result numbers

Every number in `results*/`, `final_thesis_artifacts/`, and
`thesis_overleaf_assets/` is generated by running the pipeline scripts below
against real data — nothing is computed or edited by hand. If the code or a
config changes, **rerun the relevant script(s) to regenerate results**
rather than editing a CSV, figure, or summary directly. Result folders are
also excluded from version control (see `.gitignore`) precisely so stale or
hand-edited output never gets committed as if it were a fresh run.

## Getting real data

### CICIoT2023

Download the CSV export from the official CICIoT2023 dataset page and place
the per-category folders under:

```
data/raw/ciciot2023/CIC_IOT_Dataset2023_CSV/CSV/
    Benign_Final/...
    DDoS-ICMP_Flood/...
    ... (remaining attack-category folders)
```

### NF-ToN-IoT-v2 / NF-CSE-CIC-IDS2018-v2

Download the NetFlow v2 CSV exports (UQ NIDS datasets project) and place
them under:

```
data/raw/nf_ton_iot_v2/NF-ToN-IoT-v2.csv
data/raw/nf_cse_cic_ids2018_v2/NF-CSE-CIC-IDS2018-v2.csv
```

### UNSW-NB15 / CICIDS2017 (optional, supported by the loader)

```
data/raw/unsw/UNSW-NB15_1.csv ... UNSW-NB15_4.csv, NUSW-NB15_features.csv
data/raw/cicids/Monday-WorkingHours.pcap_ISCX.csv ... (remaining days)
```

The loader auto-detects which dataset it's looking at first by filename,
then (if that's ambiguous) by column-name vocabulary — you don't need to
set `dataset:` explicitly, though `dataset: ciciot2023` / `unsw` / `cicids`
in the config (or `--dataset`) will skip detection.

## Running

**Main thesis experiment** (CICIoT2023, data placed under `data/raw/`,
default config already has `allow_synthetic_fallback: false`):

```bash
python scripts/run_all.py --config configs/default.yaml
```

**Cross-dataset generalization check** (NetFlow v2 datasets):

```bash
python scripts/run_cross_dataset.py --config configs/default.yaml
```

Individual stages of the main pipeline (each also accepts `--config`):

```bash
python scripts/run_preprocessing.py --config configs/default.yaml
python scripts/run_baselines.py --config configs/default.yaml
python scripts/run_stream_experiment.py --config configs/default.yaml
python scripts/run_active_learning.py --config configs/default.yaml
python scripts/run_rl_hybrid_experiment.py --config configs/default.yaml
```

`run_baselines.py`, `run_stream_experiment.py`, `run_active_learning.py`,
and `run_rl_hybrid_experiment.py` all read the cached split produced by
`run_preprocessing.py` from `data/processed/`, so preprocessing must run
first (this happens automatically inside `run_all.py`).

## Tests

```bash
python -m pytest tests/ -v
```

Fast, self-contained sanity checks: the label column never leaks into
features, `synthetic_data` gets stamped onto results, active learning
actually spends its label budget, the RL controller's action selection
takes no label argument (structural + behavioral), the rule layer's
`predict()` takes only features, and the cross-dataset feature-sanitization
pipeline produces finite, bounded values.

## Design notes / limitations

- The rule layer is **simulated**, not a real signature engine, and its
  `predict()` method only ever takes features — never labels (see
  `tests/test_sanity.py`). When the dataset carries a multiclass
  attack-category column, the tree is trained only on benign rows plus the
  top-K most frequent attack categories in the training prefix; rarer
  categories never enter its training set, so it structurally can't
  recognize them — the intended "rule-based systems miss novel attacks"
  behavior. For binary-only datasets it's reported as a "feature-threshold
  simulated rule layer" instead.
- Order matters for the streaming/drift/active-learning/hybrid experiments:
  `preprocess_pipeline()` produces both a shuffled stratified split (for
  batch baselines) and a chronological split (for everything stream-based).
- The drift detector's error signal uses ground-truth labels available in
  this offline simulation (standard practice for benchmarking detector
  behavior). This is separate from — and does not spend — the
  active-learning label budget, which only tracks labels actually used to
  update the model. The RL controller's action selection and the
  active-learning query decisions never see a sample's true label before
  that decision is made — only the reward/model-update step afterward does.
- The RL controller is intentionally a tabular Q-learning-lite agent, not a
  deep RL agent, per the thesis scope.
- Cross-dataset validation (`scripts/run_cross_dataset.py`) trains on one
  NetFlow v2 dataset and evaluates on a different one, using only the
  feature columns the two datasets have in common, with a dedicated
  numeric-safety pass (`sanitize_feature_matrix`) so extreme raw values
  never overflow downstream models.

## Reproducibility notes

- `configs/default.yaml` records every hyperparameter used to produce the
  thesis results, including the RL controller's reward weights (selected
  via a 27-combination reward-sensitivity sweep, see
  `results*/tables/rl_reward_tuning.csv`).
- `random_state` is set explicitly throughout; see
  `thesis_overleaf_assets/summaries/reproducibility_notes.md` (if present in
  this checkout) for the exact Python/package versions, dataset paths, and
  run commands used for the submitted thesis results.
- The submitted thesis version corresponds to repository tag
  `v1.0-thesis` — see `CODE_AVAILABILITY.md`.

## Updating this repository

See `GITHUB_UPDATE_COMMANDS.md` for the safe day-to-day workflow (and
`push_update.ps1` / `push_update.bat` for a scripted version of it) — in
short:

```bash
git status
git diff
git add -u              # stages only already-tracked, changed/deleted files
git commit -m "Update thesis codebase"
git push origin main
```

`git add -u` never picks up new/untracked files (like a freshly downloaded
dataset), so it's the safe default for routine updates. Add a genuinely new
safe file explicitly (`git add path/to/new_file`) after checking
`git status` shows only what you expect.
